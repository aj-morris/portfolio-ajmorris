# Local Favorites Tracker

A website for saving favorite local places. The categories include coffee shops, restaurants, dessert spots, and shopping. Add them to your tracker with a rating and note, so you know when you would like to return. 

## Features
You can do the following: 
- Add a place with a name, category, rating, and notes
- Search and filter by category
- Delete a place with a confirmation
- Saves everything so it's still there when you come back


## Personal Reflection 
Creating this project was a great learning process for me, as I felt concepts truly start to stick with me as I actually comprehended them. Before this project, I understood HTML and CSS more through what I could see on the page from my portfolio project. In my understanding, HTML holds the content, and CSS controls how it looks, but JavaScript is what stores the content and lets someone actually interact with it. In my Local Favorites Tracker, JavaScript lets you add favorites and search through them. Event listeners are then what actually make those actions work. For example, when you type in the search bar, the page responds by checking your favorites and showing the ones that match. Building these components helped me understand how the different parts of the page work together. 
I also learned why it made sense to put the favorites in an array instead of making an individual variable for each one. I wouldn’t know how many favorites someone might want to add, and an array lets the list grow as more get added. The code can then go through that list when it needs to display or search the favorites. LocalStorage was another important part because without it, anything someone added would disappear when they refreshed the page. Without LocalStorage there would be no point of the website because the users wouldn’t be able to see what they favorited in the future. 
The most challenging part was learning where each set of code goes because sometimes I would add code and it wouldn’t work, but it wasn’t necessarily because I had written it wrong. The code just wasn’t in a spot where it was read in the right order. I feel I had fewer issues and less need for actual debugging with JavaScript than I did with CSS. As I mentioned, my main issue was placement of the code and not larger errors.
I think the features that took longer than expected were getting the messages to show when there weren’t any favorites added and when a search did not match anything. Throughout the labs and working on the project, I actually was not aware that those were supposed to show up. When I was doing the sweep, I noticed that those were supposed to be on my tracker. I had these set up incorrectly because once I got message to show up it was showing the same one for both instances. I realized that instead of using an if and then an else if, there was the same line of code. Once I figured out what the code needed to check first, it made more sense why the messages weren’t showing when I wanted them to. If I did this again, I would test those two situations separately as I added the code.
After I had the main parts of the tracker working, I took extra time to add some of the optional enhancements. I added a better error message that shows up next to the field that needs to be fixed instead of only appearing as a pop-up. I also added a way to filter favorites by rating, which gives someone another way to narrow down their list. The counter shows how many favorites are being displayed and changes when someone searches or filters. Finally, I added a clear all button with a confirmation so someone can start over without accidentally deleting everything. These additions took more time, but I wanted the tracker to feel more useful and easier to understand when someone was actually using it.
I think the biggest help during my problem-solving process was the lab guide. Throughout this process, I was able to work to really grasp what I was doing by having the lab guide explain segments and break down the code to a point where I could understand it. I feel that there were some tricky parts in the lab where I just didn’t understand where the code was supposed to go and how it affected other parts. In these moments, I would review the slideshows, and if that couldn’t answer my question, I would ask the lab guide. I learned that you have to be very specific when asking the lab guide questions. My process would start with copying the specific code I had written or pulled from the lab and then asking individual questions one at a time. This was also helpful if there was an error and I couldn’t seem to find it. I would copy and paste the code and have the lab guide run through it. It could help me spot the issue, but I still had to solve it on my own by understanding the explanation and checking that the page worked afterward. The lab guide is a super helpful resource because it has the lab content fed into it so understands where we are at and where it can support. 
If I were going to use this tracker every day, I would want to add categories like restaurants, recipes, TV shows, and movies. I would put separate pages for each category at the top so I could see all my favorites in one category and then search within that section. That would make it easier to use if I added hundreds of favorites instead of having everything in one long list. I think it has the potential to become more like a diary where I could keep track of different aspects of my life and look back on what I was enjoying at different times. I really enjoyed working on this project and feel like the code is finally clicking with me. I am looking forward to the remaining projects throughout this class, as I continue to become more comfortable with the code.
